📄 DOM（Document Object Model）とは？

▼

DOMは、Webページの中身を「木構造」として表現したものです。 JavaScriptから「ページのテキストを変更する」「ボタンを追加する」などの操作ができるのは、DOMのおかげです。

DOM ツリーの例
<html>
<head>
<title> マイページ
<body>
<h1> ようこそ
<p> これは段落です
💡 重要： JavaScriptは同じオリジン内のDOMしか操作できません。 これが同一オリジンポリシー（SOP：Same-Origin Policy）の基本です。

🌐 オリジン（Origin）とは？

▼

オリジンは、Webサイトを識別するための「住所」のようなものです。 次の3つの要素の組み合わせで決まります。

📖 重要な用語

✓ 同一オリジン (Same-Origin)
2つのURLのオリジンが完全に一致する状態。 スキーム・ホスト・ポートの3要素すべてが同じであること。
例：https://example.com/page1 と https://example.com/page2
✗ クロスオリジン (Cross-Origin)
2つのURLのオリジンが異なる状態。 スキーム・ホスト・ポートのうち1つでも違うと、クロスオリジンになる。
例：https://example.com と http://example.com（スキーム違い）
💡 覚えておこう： 同一オリジン間では自由にアクセスできますが、クロスオリジン間ではブラウザーが制限をかけます。 これが同一オリジンポリシー（SOP：Same-Origin Policy）の基本原則です。
オリジンの比較例

2つのURLを比較して、「同一オリジン」か「クロスオリジン（異なるオリジン）」かを判定します。

アクセス元 アクセス先 判定 理由
https://example.com/page1 https://example.com/page2 ✓ 同一 パスが違うだけ（/page1 → /page2）
https://example.com/page1 https://example.com/page1?id=123 ✓ 同一 クエリパラメーターはオリジンに含まれない
https://example.com/page1 https://example.com/page1#section ✓ 同一 フラグメント（#以降）はオリジンに含まれない
https://example.com/page1 https://example.com:443/admin ✓ 同一 ポート:443はhttpsのデフォルト（省略可）
https://example.com/page1 http://example.com/page1 ✗ 異なる スキーム違い（https → http）
https://example.com/page1 https://sub.example.com/page1 ✗ 異なる ホスト違い（example.com → sub.example.com）
https://example.com/page1 https://example.org/page1 ✗ 異なる ホスト違い（.com → .org）
https://example.com/page1 https://example.com:8080/page1 ✗ 異なる ポート違い（:443 → :8080）
https://example.com/page1 http://other.com:8080/page1 ✗ 異なる すべて違う（スキーム・ホスト・ポート）

※ ポート番号は省略されることがあります（https は 443、http は 80 がデフォルト）

SOP 実験

同一オリジンポリシー（SOP）とは？

同一オリジンポリシー（SOP：Same-Origin Policy）は、Webブラウザーの基本的なセキュリティルールです。 「オリジンスキーム（http/https）、ホスト（ドメイン名）、ポート番号の3つの組み合わせ」が異なるページ同士は、 お互いのページの中身（DOM）を勝手に読んだり書き換えたりできません。

なぜ重要？ 例えば、悪意あるサイトがあなたの銀行サイトの情報を盗もうとしても、SOPがあるから防げます。

ここではiframeとsandbox属性を使って、同一オリジンとクロスオリジンの状況を意図的に作り出し、 SOPによる「見えるけど触れない」という制約を体感します。

※ sandbox属性：iframeを隔離環境で実行する仕組み。allow-same-originを付けないと、同じサイトでもクロスオリジン扱いになります。

postMessage デモ

postMessage：SOPの壁を越える安全な通信手段

postMessageは、異なるオリジン間でメッセージを安全にやり取りするためのJavaScript APIです。 SOPにより通常はDOMアクセスがブロックされますが、postMessageを使えばメッセージの送受信だけは可能です。

なぜ安全？ postMessageは「データを渡す」だけで、「DOMを操作する」ことはできません。 受信側は送信元のオリジンを確認してから処理できるため、信頼できる相手とだけ通信できます。

postMessageの仕組み
1
親ページ（このページ）が子ページ（iframe）に向けてメッセージを送信
iframe.contentWindow.postMessage(data, '*')
↓
2
子ページ（iframe内）がメッセージを受信
window.addEventListener('message', (event) => {...})
↓
3
子ページが親ページに返信を送信
双方向のメッセージ交換が可能

実験手順

  1. 送信先を選択：同一オリジンiframe または sandbox iframe
  2. メッセージを入力：送りたい文字列を入力
  3. 「postMessage 送信」ボタンをクリック
  4. 受信ログを確認：親→子へのメッセージ送信、子→親からの返信が表示されます

※ iframeからの返信は自動的に親ページに送られ、下の受信ログに表示されます。

📖 CORS（Cross-Origin Resource Sharing）とは？

            ▼
          

          

            

              
CORSの基本的な流れ

              

                

                  
🌐

                  
アクセス元

                  

                    このページ

                    https://your-site.com

                    ブラウザー上で動作
                  

                


                

                  

                    

                      
① リクエスト送信

                      
───────►

                      
データが欲しい！

                    

                  

                  

                    

                      
② レスポンス返却

                      
◄───────

                      
CORSヘッダー付きで返す

                    

                  

                  

                    

                      ③ ブラウザーがチェック

                      CORSヘッダーを確認して、
許可/ブロックを判定
                    

                  

                


                

                  
🖥️

                  
アクセス先

                  

                    外部サーバー

                    https://api.example.com

                    データを提供する側
                  

                

              

            


            

              CORSは、「アクセス元（このページ）」が「アクセス先（外部サーバー）」からデータを取得したいときに使う仕組みです。
              SOPで原則ブロックされますが、サーバーが「このオリジンからのアクセスはOK」と宣言すれば、ブラウザーが許可します。
            


            

              🎯 重要概念：
              CORSはサーバー側の「許可証」です。ブラウザーは勝手にリクエストを送りますが、
              サーバーが適切なヘッダーを返さないと、ブラウザーがレスポンスをブロックします。
              CORSのチェックはブラウザーが行います。リクエスト自体はサーバーに届きますが、
              レスポンスを読み取れるかどうかはブラウザーが判断します。
            

          

        

      


      
      

        

          

            
🔄 シンプルリクエストとプリフライトリクエスト

            ▼
          

          

            

              CORSリクエストには2つの種類があります。
              どちらになるかは、リクエストの条件によって自動的に決まります。
            


            
            

              

                ✓
                シンプルリクエスト（Simple Request）
                ＝ 単純リクエスト
              

              

                

                  特定の条件をすべて満たす場合、ブラウザーはプリフライトなしで直接リクエストを送信します。
                  サーバーからのレスポンスに適切なCORSヘッダーがあれば、そのまま成功します。
                

              


              

                
✓ シンプルリクエストの条件（すべて必要）

                
    
                  
  1. 
                    メソッドが以下のいずれか：
                    
    
                      GET, HEAD, POST
                    
    
                  
    2. 
                  
  2. 
                    Content-Typeが以下のいずれか（POSTの場合）：
                    
    
                      text/plain
    
                      application/x-www-form-urlencoded
    
                      multipart/form-data
                    
    
                  
    3. 
                  
  3. 
                    カスタムヘッダーが以下のセーフリストのみ：
                    
    
                      Accept, Accept-Language, Content-Language, Content-Type
                    
    
                  
    4.

                    1
                    ブラウザーが直接リクエスト送信
                  

                  
↓

                  

                    2
                    サーバーがCORSヘッダー付きでレスポンス
                  

                  
↓

                  

                    3
                    ブラウザーがCORSヘッダーをチェック
                  

                  
↓

                  

                    ✓
                    許可 → JavaScriptがレスポンスを取得
                  

                

              

            


            
            

              

                ⚠️
                プリフライトリクエスト（Preflight Request）
              


              

                📖 「プリフライト（Preflight）」とは？
                

                  Pre-（事前の）+ Flight（飛行） = 飛行前 という意味です。
                  飛行機が離陸前に行う安全確認のことを指し、転じて「本番の処理の前に行う事前確認」という意味で使われます。
                

                

                  技術的には： ブラウザーが本リクエストの前に自動的に送る「OPTIONSメソッドのリクエスト」のことです。
                  サーバーが「このリクエストを受け入れるか」を事前にチェックできます。
                

              


              

                

                  シンプルリクエストの条件を1つでも満たさない場合、ブラウザーは本リクエストの前にOPTIONSメソッドで事前確認します。
                  これにより、サーバーが「このリクエストを受け入れるか」を事前にチェックできます。
                

              


              

                
⚠️ プリフライトが発生する例

                
    
                  
  • PUT, PATCH, DELETE などの非セーフメソッドを使用
    • 
                  
  • application/json, application/xml などの非セーフContent-Typeを使用
    • 
                  
  • Authorization, X-Requested-With などのカスタムヘッダーを追加
    • 
                

              


              

                
📋 プリフライトリクエストの流れ

                

                  

                    1
                    ブラウザーがOPTIONSリクエスト送信（プリフライト）
                  

                  
↓

                  

                    2
                    サーバーが許可内容を返す（ACAM, ACAH等）
                  

                  
↓

                  

                    3
                    ブラウザーがプリフライトレスポンスをチェック
                  

                  
↓

                  

                    ✓
                    許可されていれば本リクエスト送信
                  

                  
↓

                  

                    4
                    サーバーが本レスポンスを返す
                  

                  
↓

                  

                    ✓
                    JavaScriptがレスポンスを取得
                  

                

              

            


            

              💡 重要ポイント：
              
    
                
  • シンプルリクエストは条件が厳しく、実際のWebアプリではほとんどプリフライトが発生します
    • 
                
  • ブラウザーがプリフライト（OPTIONS）を自動的に送るため、開発者が意識する必要はありません
    • 
                
  • プリフライトで許可されない場合、本リクエストは送信されません
    • 
                
  • DevToolsのNetworkタブでOPTIONSメソッドを確認すると、プリフライトの詳細がわかります
    • 
              

            

          

        

      


      
      

        

          

            
📚 用語集：CORS用語の完全ガイド

            ▼
          

          

            

              CORSの学習でよく出てくる用語を整理しました。実験を進める前に、ここで確認しておくとスムーズです。
            


            
            

              
🔹 セーフメソッド（Safe Methods）

              

                シンプルリクエストとして扱われる可能性があるHTTPメソッドです。
                ただし、他の条件（Content-Typeやヘッダー）も満たす必要があります。
              

              

                

                  GET
                  リソースの取得（もっとも一般的）
                

                

                  HEAD
                  ヘッダー情報のみ取得
                

                

                  POST
                  データの送信（Content-Type制限あり）
                

              

              

                ⚠️ PUT、PATCH、DELETEなどはセーフメソッドではないため、
                必ずプリフライト（事前確認のOPTIONSリクエスト）が発生します。
              

            


            
            

              
🔹 セーフリスト（Safe List）

              

                プリフライトなしで送信できるContent-Typeとリクエストヘッダーのリストです。
              


              
✓ セーフなContent-Type

              

                

                  text/plain
                  プレーンテキスト
                

                

                  application/x-www-form-urlencoded
                  HTMLフォーム送信のデフォルト形式
                

                

                  multipart/form-data
                  ファイルアップロード用
                

              

              

                ⚠️ application/json、application/xmlなどは非セーフリストなので、
                プリフライトが発生します。
              


              
✓ セーフなリクエストヘッダー

              

                

                  Accept
                  受け入れ可能なレスポンス形式
                

                

                  Accept-Language
                  希望する言語
                

                

                  Content-Language
                  コンテンツの言語
                

                

                  Content-Type
                  上記の3種類のいずれかの場合のみ
                

              

              

                ⚠️ Authorization、X-Requested-Withなどは非セーフリストなので、
                プリフライトが発生します。
              

            


            
            

              
🔹 CORSレスポンスヘッダー（サーバーが返すヘッダー）

              

                サーバーがブラウザーに対して「このリクエストは許可します」と伝えるためのヘッダーです。
              


              

                

                  Access-Control-Allow-Origin
                  （ACAO）
                

                

                  役割：どのオリジンからのアクセスを許可するか指定します。
                

                

                  

                    Access-Control-Allow-Origin: https://example.com
                    → 特定の1つのオリジンを許可
                  

                  

                    Access-Control-Allow-Origin: *
                    → すべてのオリジンを許可（ワイルドカード）
                  

                

                

                  ⚠️ 重要な制約：
                  
    
                    
  • 
                      複数のオリジンを指定できません。
                      カンマ区切りでhttps://example.com, https://other.comのように列挙することはできません。
                      指定できるのは1つのオリジンまたはワイルドカード（*）のみです。
                    
    • 
                    
  • 
                      複数のオリジンからのアクセスを許可したい場合、サーバー側でリクエストのOriginヘッダーを確認し、
                      許可するオリジンのリストと照合した上で、動的に該当オリジンを返す実装が必要です。
                    
    • 
                    
  • 
                      すべてのオリジンを許可したい場合は、ワイルドカード（*）を使います。
                      ただし、withCredentials: trueの場合、*は使えません。具体的なオリジンを指定する必要があります。
                    
    • 
                  

                

              


              

                

                  Access-Control-Allow-Credentials
                  （ACAC）
                

                

                  役割：Cookie や認証情報を含むリクエストを許可するかどうか指定します。
                

                

                  

                    Access-Control-Allow-Credentials: true
                    → 資格情報を含むリクエストを許可
                  

                

                

                  ⚠️ withCredentials: trueでリクエストする場合、このヘッダーは必須です。
                

              


              

                

                  Access-Control-Allow-Methods
                  （ACAM）
                

                

                  役割：プリフライトで、どのHTTPメソッドを許可するか指定します。
                

                

                  

                    Access-Control-Allow-Methods: GET, POST, PUT, DELETE
                    → 指定したメソッドを許可
                  

                

                

                  ⚠️ プリフライト（OPTIONS）レスポンスで返す必要があります。本リクエストのメソッドが含まれていないと、リクエストがブロックされます。
                

              


              

                

                  Access-Control-Allow-Headers
                  （ACAH）
                

                

                  役割：プリフライトで、どのカスタムヘッダーを許可するか指定します。
                

                

                  

                    Access-Control-Allow-Headers: Authorization, Content-Type
                    → 指定したヘッダーを許可
                  

                

                

                  ⚠️ プリフライト（OPTIONS）レスポンスで返す必要があります。非セーフリストヘッダーが含まれていないと、リクエストがブロックされます。
                

              

            


            

              💡 まとめ：
              
    
                
  • セーフメソッド・セーフリストは、プリフライトを避けるための条件
    • 
                
  • ACAOはもっとも重要なCORSヘッダーで、これがないとすべてブロックされる
    • 
                
  • ACACは資格情報（Cookie等）を送る場合に必須
    • 
                
  • ACAMとACAHは、プリフライトでサーバーが「何を許可するか」を宣言するヘッダー
    •
